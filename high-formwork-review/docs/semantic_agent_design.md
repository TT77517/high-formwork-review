## 目标架构

### 1. 核心能力
- **语义理解**: 基于 LLM 理解方案文本的语义
- **上下文感知**: 理解条款在整体方案中的上下文
- **逻辑推理**: 判断方案是否满足规范的逻辑要求
- **证据提取**: 自动提取支持判断的关键证据

### 2. 架构设计

```
┌─────────────────────────────────────────────────────────┐
│                   规范语义审查 Agent                      │
├─────────────────────────────────────────────────────────┤
│  输入层                                                   │
│  ├─ MinerUDocument (解析后的方案文档)                     │
│  ├─ 语义规则库 (84条规则)                                 │
│  └─ ProjectFacts (项目基础信息)                           │
├─────────────────────────────────────────────────────────┤
│  处理层                                                   │
│  ├─ 证据提取器 (Evidence Extractor)                       │
│  │   ├─ 关键词匹配 (快速召回)                             │
│  │   ├─ 章节定位 (基于目录结构)                           │
│  │   └─ 上下文扩展 (前后文关联)                           │
│  ├─ Prompt 构建器 (Prompt Builder)                        │
│  │   ├─ 规则摘要生成                                      │
│  │   ├─ 证据文本组织                                      │
│  │   └─ 审查指令封装                                      │
│  └─ LLM 推理引擎 (LLM Engine)                           │
│      ├─ Dify Workflow (可选)                              │
│      ├─ 直接 API 调用 (备选)                              │
│      └─ 结果解析与验证                                    │
├─────────────────────────────────────────────────────────┤
│  输出层                                                   │
│  ├─ 审查结果 (COMPLIANT/VIOLATED/UNCERTAIN/N/A)          │
│  ├─ 判定理由 (自然语言解释)                               │
│  ├─ 证据引用 (原文片段 + 页码)                            │
│  └─ 整改建议 (如违规)                                     │
└─────────────────────────────────────────────────────────┘
```

### 3. 实现方案

#### 方案 A: Dify Workflow 集成（推荐）
**优点**:
- 已有 Dify 基础设施（completeness_review 已使用）
- 可视化配置 prompt
- 支持版本管理和 A/B 测试
- 可追踪调用历史和成本

**实现步骤**:
1. 在 Dify 中创建语义审查 Workflow
2. 设计输入 Schema（规则列表 + 方案文本）
3. 设计输出 Schema（审查结果 JSON）
4. 实现 `run_semantic_engine_dify()` 函数
5. 添加配置开关（`SEMANTIC_REVIEW_MODE=local|dify`）

#### 方案 B: 直接 LLM API 调用
**优点**:
- 更灵活的控制
- 不依赖外部服务
- 可自定义重试和降级策略

**实现步骤**:
1. 选择 LLM 提供商（OpenAI/Anthropic/本地模型）
2. 实现 API 客户端
3. 设计 prompt 模板
4. 实现结果解析和验证
5. 添加错误处理和降级机制

### 4. 关键改进点

#### 4.1 证据提取优化
```python
# 当前：简单关键词匹配
keywords = ["编制单位", "施工单位", "总承包"]
matched = any(kw in text for kw in keywords)

# 改进：多层次证据提取
1. 关键词召回（快速筛选相关章节）
2. 章节定位（基于目录结构找到对应章节）
3. 上下文扩展（提取前后段落）
4. 证据排序（按相关性和重要性排序）
```

#### 4.2 Prompt 工程
```python
# 系统提示
SYSTEM_PROMPT = """你是高支模专项施工方案审查专家。
你的任务是对照规范条款，审查方案文本是否满足要求。

审查原则：
1. 严格依据规范原文判断
2. 关注实质性内容，而非形式
3. 考虑工程实际情况
4. 给出明确的判定和理由
"""

# 用户提示模板
USER_PROMPT_TEMPLATE = """
请审查以下方案内容是否满足规范要求：

【规范条款】
{rule_content}

【方案相关内容】
{evidence_text}

请输出 JSON 格式的审查结果：
{{
  "status": "COMPLIANT/VIOLATED/UNCERTAIN/NOT_APPLICABLE",
  "reason": "判定理由",
  "evidence_quote": "方案原文引用"
}}
"""
```

#### 4.3 结果后处理
- **一致性检查**: 确保相同内容的规则判定一致
- **冲突检测**: 识别相互矛盾的判定结果
- **置信度评估**: 基于证据充分度给出置信度分数
- **人工复核标记**: 对低置信度结果标记为需人工复核

### 7. 风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|----------|
| LLM 幻觉 | 给出错误判定 | 强制引用原文证据，添加后处理验证 |
| 响应延迟 | 用户体验差 | 异步处理，进度反馈，缓存机制 |
| 成本控制 | API 费用过高 | 批量处理，缓存结果，本地模型备选 |
| 规则覆盖不全 | 部分规则无法审查 | 渐进式扩展，人工补充规则 |
